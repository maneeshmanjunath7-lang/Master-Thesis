\section{Purpose of the Task Dataset}
The simulator starts from a task table, not from radiance measurements or images. Each row represents a fire region for which a follow-up observation may be requested. The main preprocessing decision is how to turn many thermal pixels into distinct tasks. Keeping every pixel would repeatedly request the same fire, whereas aggressive merging could hide separate events. Source-product identifiers are therefore preserved and duplicates are removed before any architecture is evaluated.

Two three-day windows were selected. The California window, 3--5 July 2025, includes the early Madre Fire; the India window, 14--16 April 2026, produces a much denser set of requests. After preprocessing, California has 32 tasks and India has 773. These are two engineering cases rather than a sample of global fire behaviour. Any California--India difference therefore includes the chosen events, geography, timing, density, and priority mix. The report describes this as a workload contrast, not a general regional effect.

Figure~\ref{fig:task_map} shows where the retained tasks lie. The map uses the US Census Bureau boundary for California and Natural Earth for India \citep{USCensus2025Boundaries,NaturalEarth2025}. Selection itself is performed with event bounding boxes, not political polygons. A few accepted coordinates can therefore appear outside the drawn administrative outline. They remain visible in the figure because clipping them would conceal the effect of the stated filter.

\section{Processing Sequence}
Figure~\ref{fig:task_pipeline} records the actual processing order. Filtering decides which detections are eligible; clustering groups nearby detections into candidate fire regions; scoring assigns an engineering priority; and de-duplication decides which candidates remain separate tasks. Keeping these stages distinct is important because each one changes the eventual communication load in a different way.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.96\textwidth]{figures/part1_revision/task_pipeline.png}
\caption{Traceable task-generation workflow. Filtering occurs before clustering, and the exported task retains source-product provenance.}
\label{fig:task_pipeline}
\end{figure}
Each downloaded \texttt{.SEN3} directory is one Sentinel-3 SLSTR Level-2 FRP granule. The code reads its sensing interval, extracts geolocated fire pixels from the primary FRP NetCDF file, applies the event-window and region filters, and rejects invalid coordinates or FRP values. The original product identifier is carried into the task output, so a simulated row can be traced back to the input granule.

De-duplication is applied at four levels:

\begin{enumerate}
\item Each Sentinel-3 product is read once.
\item Only the primary FRP NetCDF content is used for fire pixels.
\item Exact and near-duplicate hotspot rows are removed using position, time, and FRP.
\item Candidate tasks that represent the same fire region on the same day are merged, retaining a traceable representative and the strongest priority evidence.
\end{enumerate}
The reduction in reported FRP during pipeline development reflects removal of repeated records; it is not evidence of a physical decrease in fire activity.

\section{FRP Filtering and DBSCAN Clustering}
The development pipeline applies an FRP inclusion threshold of 10 MW before spatial grouping. This threshold is an engineering rule for generating communication tasks, not a definition of wildfire occurrence.

Density-Based Spatial Clustering of Applications with Noise (DBSCAN) is used because the number of fire regions is not known in advance. DBSCAN connects detections that have enough neighbours within a chosen distance. Here, \texttt{eps} is the neighbourhood radius and \texttt{min\_samples} is the minimum number of detections required for a dense cluster. The documented baseline uses a 10 km neighbourhood and \texttt{min\_samples = 3}.

The filters are applied before DBSCAN. This prevents detections outside the selected date, region, quality, or FRP range from influencing a cluster. DBSCAN is then run on the remaining positions for the declared grouping unit. Dense detections form a cluster, while isolated detections follow the stated noise-point rule instead of being assigned to the nearest cluster without evidence. The exported row stores the centroid, approximate radius, contributing-detection count, and product provenance. The totals in Table~\ref{tab:task_population} are therefore task totals after filtering and de-duplication, not raw pixel counts.

The clustering choice controls network load. A smaller radius creates more packets and can fragment one event. A larger radius creates fewer packets and can merge independent events. The baseline must therefore be interpreted together with the proposed 5 km and 20 km sensitivity checks.

\section{Confidence and Priority}
Sentinel-3 supplies numerical MWIR confidence information. FIRMS VIIRS uses categorical low, nominal, and high values. FIRMS confidence is used only during screening and is mapped to 0.33, 0.66, and 1.00 for visualization or contextual comparison. The final simulation score uses the Sentinel-3-derived value. It is a relative ranking input, not a calibrated probability of wildfire.

Invalid Sentinel-3 confidence values are flagged as missing. A neutral value of 0.50 is used in the score so that an unavailable field does not automatically suppress the task. The missing fraction and the original confidence summaries remain in the exported data.

The FRP component combines normalized total and maximum FRP:

\begin{quote}\texttt{S\_FRP = 0.60 * N(log(1 + FRP\_total)) + 0.40 * N(log(1 + FRP\_max)).}\end{quote}
The task score is:

\begin{quote}\texttt{S\_task = 0.50 * S\_FRP + 0.30 * S\_conf + 0.20 * S\_cluster.}\end{quote}
The notation is used consistently: \texttt{S\_FRP} is the intensity term, \texttt{S\_conf} the confidence term, \texttt{S\_cluster} the spatial-support term, and \texttt{S\_task} the final score. The weights express an engineering preference for energetic strength while retaining confidence and spatial support. They were not fitted to emergency-service labels and must not be interpreted as an official severity model.

These sizes represent structured requests, associated metadata, and protocol allowance. They are not image products. This separates data-volume sensitivity from urgency.

\section{Dataset Validation and Limits}
The Madre Fire provides one event-level plausibility check. Sentinel-3 and FIRMS both show strong detections near the reported event during the California window. Agreement at that location and time supports the corresponding California task, but it is not a validation of all 805 tasks, of the priority score, or of wildfire-classification accuracy. An equivalent named-incident link was not established for every India task.

The dataset has additional limits. Bounding-box filtering can retain detections outside a political boundary. Cloud, smoke, sampling, and overpass time affect what either sensor records, and FIRMS and Sentinel-3 totals cannot be compared directly without spatial and temporal matching. A different sensor, season, threshold, clustering rule, event mix, or priority mapping would create a different workload and could change the architecture ranking.

The task table is frozen before the architecture sweep. Every case within an event window therefore receives the same release times and task definitions. This makes architecture comparisons controlled within a region. It does not turn the two selected windows into population-level evidence for California or India.
